# Yio AI 大赛申报材料

更新日期：2026 年 9 月 29 日

## 一句话简介

Yio 是一套面向 AI 协作开发的跨引擎游戏 UI 框架，让 AI 使用熟悉的标准 HTML/CSS 编写界面，再通过围栏校验、类型化运行时 API、Rust 自绘核心和 Unity 后端，将“能生成的 UI”变成“可验证、可运行、可持续维护的游戏工程资产”。

## 项目简介

Yio 解决的是 AI 参与游戏 UI 开发时“会生成，但难以稳定落地”的问题。传统游戏 UI 通常依赖专用编辑器、私有二进制格式和引擎绑定组件，AI 很难直接理解界面结构、预测渲染结果，也难以安全修改。Yio 选择标准 HTML/CSS 子集作为设计期语言，利用 AI 对 Web 语义的强先验，让 AI 能直接阅读、生成和修改 UI；同时通过打包期围栏验证拒绝不支持或含义不确定的写法，通过类型化对象树、Rust 跨引擎核心、自绘渲染和 C# 投影层保证运行时能力。项目已形成从 AI 初始化、界面编写、浏览器预览、自动检查、资源打包到 Unity 运行的完整闭环，并提供 CLI、桌面 GUI、Unity UPM 包、22 个场景化展示页面及自动化测试体系。Yio 的目标不是让 AI 生成一次性 Demo，而是为游戏 UI 建立一条 AI 可理解、机器可验证、团队可维护、未来可跨引擎复用的生产链路。

# 一、项目背景

## 1 项目起因

生成式 AI 已经能够快速编写网页，但在游戏 UI 领域，AI 的能力往往停留在“生成代码片段”或“制作静态效果图”，距离真正进入生产流程仍有明显断层。

传统游戏 UI 方案通常依赖引擎专属编辑器、私有组件体系或二进制资源格式。界面的结构、样式、交互和资源关系分散在场景、Prefab、Inspector 配置与脚本中。对人类开发者而言，这种方式可视化程度较高；但对 AI 而言，它缺少稳定、可读、可批量修改的文本表示，也难以仅凭代码判断最终画面。即使 AI 生成了脚本，仍可能出现组件类型不匹配、布局语义不一致、引擎版本差异、资源遗漏或运行时行为不可控等问题。

另一方面，直接把浏览器或完整 Web 技术栈嵌入游戏也并非理想答案。完整浏览器能力过重，渲染和运行时边界难以控制，并且很难满足游戏 UI 对自绘、批处理、动画、遮罩、世界空间挂载和跨引擎一致性的要求。

Yio 因此提出一个不同的问题：能否保留 HTML/CSS 对 AI 最友好的表达方式，同时只实现游戏 UI 真正需要、且能够被框架完整兑现的一组语义？

## 2 要解决的核心痛点

第一，解决 AI 难以理解和修改传统游戏 UI 资产的问题。Yio 使用文本化的 HTML/CSS 作为设计期 DSL，界面结构、样式和语义都可被 AI 直接读取与编辑，也适合 Git 版本管理和代码评审。

第二，解决 AI 生成结果“不确定”的问题。Yio 不宣称支持完整浏览器，而是建立明确的 HTML/CSS 围栏。超出能力范围的标签、属性、选择器、属性值和控件结构会在打包期直接报错，而不是静默忽略或在运行时产生不可预测结果。

第三，解决设计语言与游戏运行时脱节的问题。HTML 标签和 WAI-ARIA 角色会映射为稳定的 `Container`、`Button`、`Slider`、`ListView`、`Tree` 等类型化对象。游戏业务代码操作的是明确的对象、属性和事件，而不是脆弱的字符串命令或全局句柄。

第四，解决单一引擎绑定带来的重复建设问题。Yio 将布局、文本、滚动、动画、输入语义和渲染意图集中在 Rust 核心中，引擎后端只负责输入采集、资源加载和渲染对象映射。Unity 是首个落地后端，核心架构已为 Godot 等后续引擎预留边界。

# 二、项目介绍

## 1 项目说明

### 1.1 解决方案与主要功能

Yio 已经形成一条完整的游戏 UI 生产链路。

在设计期，开发者或 AI 使用标准 HTML/CSS 子集描述界面。普通结构使用 `div`、`span`、`button`、`img` 等标准元素，Slider、ListView、TabList、Tree 等复杂控件使用 WAI-ARIA `role` 表达，不额外创造一套只有框架自己理解的标签语言。这样既继承了 AI 对 Web 开发的大量训练先验，也保留了标准语义的可读性。

在校验与打包阶段，Yio Fence 对标签、属性、CSS、控件结构和资源引用进行检查。框架坚持“无法兑现就明确拒绝”，例如不支持的 CSS 不会被悄悄忽略，可能导致浏览器预览与运行时分叉的写法也会被诊断。合法内容随后被打包为二进制 UI 包、图集和字体资源。

在运行时，Rust 核心负责 CSS 层叠、布局、文本排版、滚动与惯性、动画、命中测试、事件路由、虚拟列表、裁剪遮罩和渲染树构建。C ABI 将引擎中立的帧数据传给后端，Unity 侧通过 C# 类型化 API 和渲染镜像完成集成。业务开发者可以查询和操作按钮、列表、文本框等对象，监听点击、选择、拖拽、焦点和页面切换事件，也可以在运行时增删节点、修改样式和创建动画。

围绕核心框架，项目还提供：

- `yio` CLI：覆盖初始化、校验、构建、预览、资源管理、脚手架、版本检查和 Unity 导入验证。
- Tauri 桌面打包器：为不习惯命令行的成员提供图形化工作流。
- Unity UPM 包：通过 Git URL 安装，包含运行时、原生库、CLI 和 GUI 工具。
- AI Skills 与安装手册：AI 可按照标准流程完成安装、工作区初始化、版本同步和开发自检。
- 浏览器预览与矩形差分工具：在进入 Unity 前快速检查布局，并将浏览器 DOM 与 Rust 核心布局结果进行自动对比。
- Showcase 工程：包含首页、角色、背包、商城、邮件、表单、动画、运行时 CSS、形状遮罩、滑动翻页、纹理逐出、压力测试等 22 个场景化页面。

### 1.2 思考过程与关键决策

项目最关键的决策，是没有把 AI 当作附加在传统工具上的聊天入口，而是从底层重新设计 UI 的表达和验证方式。

第一项决策是使用标准 HTML/CSS 子集，而不是自创 DSL。AI 对 HTML/CSS 的训练数据和结构先验远高于引擎私有格式；采用标准语义后，AI 不仅能生成文本，还能较准确地推断布局与视觉结果。与此同时，Yio 通过围栏控制实现边界，避免“表面兼容 Web、实际处处不一致”。

第二项决策是让标签和 ARIA 语义决定稳定类型，让 CSS 只负责视觉与布局策略。这样修改样式不会把一个对象从按钮变成容器，运行时 API 可以保持强类型，AI 和业务代码都更容易推理。

第三项决策是坚持自绘和跨引擎核心。Yio 没有把 Unity 的 GameObject 或某个引擎组件模型扩散到公共层，而是通过 Rust 核心统一计算，再由后端执行。这提高了跨引擎复用的可能性，也使同一份 UI 包可以获得一致的布局与交互语义。

第四项决策是把“AI 是否能安全完成闭环”作为产品验收标准。项目不仅提供语法说明，还把操作手册、参考资料和错误修复方法随 CLI 脚手架分发给消费侧 AI；命令支持结构化 JSON 输出和明确退出码，便于 AI 自动判断成功、内容错误或工具错误。

### 1.3 过程记录与阶段结果

截至 2026 年 9 月 29 日，项目已经完成从概念验证到可运行工程体系的主要闭环：

- 已发布 v0.0.1 至 v0.0.18 共 18 个版本，持续迭代核心能力与 Unity 集成。
- Rust 工作区包含 core、fence、ffi、packer CLI、packer GUI、xtask 六个模块，并形成 Unity UPM 包。
- 仓库包含 1,100 余个文件、约 11.7 万行 Rust 代码和约 7,200 行 Unity 包 C# 代码。
- 可检索到约 2,100 个 Rust 测试标记和近 500 个 C# 测试标记，覆盖围栏、布局、渲染、输入、列表、FFI、公共 API 与镜像策略等环节。
- Showcase 已建设 22 个顶层场景页面，用真实游戏 UI 形态验证首页、商城、背包、邮件、表单、树控件、滚动、动画、遮罩、运行时样式和压力场景。
- 在约 2,400 节点的基准场景中，增量布局实测由每帧全量重建约 29.8ms 降至稳态约 3.1ms，约提升 9.5 倍；单点变更约 2.4ms。
- 在 500 条血条压力场景中，增量渲染构建稳态约 9ms，对照全量重建约 16.9ms，耗时接近减半。
- 项目建立了浏览器与核心布局的 rect-diff 对拍、增量与全量重建差分守卫、包格式版本门、ABI 尺寸断言、CI 格式与静态检查等质量机制。

AI 在项目中的使用不是一次性的辅助生成，而是贯穿需求分析、架构讨论、HTML/CSS 页面拼装、测试补充、文档同步、错误诊断和跨层验收。更重要的是，Yio 将这些经验固化成产品能力：消费侧 AI 获得明确的技能说明、命令接口、机器可读诊断和可重复验证流程，而不是依赖开发者个人提示词。

目前项目处于开源技术验证和真实工程打磨阶段，用户与业务反馈主要来自框架自身 Showcase、Unity 集成闭环和持续版本迭代，尚未开展大规模商业用户统计。因此申报材料不虚构 DAU、节省人日或商业收入，而以可复现的功能、测试、性能基准和完整工具链作为现阶段成果证据。

建议演示视频控制在 3 至 5 分钟，并按照以下顺序展示：

1. 用一句自然语言提出修改需求，例如“把背包界面改成左右双栏，选中物品后显示详情和操作按钮”。

7. 最后用架构图说明同一份 Rust 核心未来可连接不同游戏引擎。

# 三、项目创新性

## 1 为 AI 重新设计游戏 UI 的中间表示

多数 AI UI 产品关注“如何让模型生成界面”，Yio 更关注“生成结果如何成为可靠的游戏工程资产”。项目把标准 HTML/CSS 子集作为人、AI、工具链共同使用的中间表示，使设计意图可读、可比较、可版本管理，也能直接利用通用大模型已有的 Web 知识。

这不是简单地把网页放进游戏。Yio 只选择能够在自绘游戏运行时完整兑现的语义，并建立严格围栏。标准语义提供 AI 先验，围栏提供工程确定性，两者结合形成项目最核心的创新。

## 2 将 AI 生成从概率结果变成可验证流水线

AI 生成内容天然具有不确定性。Yio 用多层机器验证降低这种不确定性：语法和结构由 Fence 校验；资源和包由 CLI 校验；浏览器预览与核心布局可做矩形差分；增量算法与全量算法可做逐节点对拍；FFI 和包格式有版本与尺寸门；Unity 产物还可通过批处理导入验证。

因此，AI 不必“猜测是否正确”，而是可以执行命令、读取结构化结果、定位错误、修改并再次验证。这使 AI 从代码建议者变成能够完成闭环的工程协作者。

## 3 标准语义与类型化游戏运行时的结合

HTML/CSS 擅长表达结构和样式，但游戏业务需要稳定的对象类型、生命周期、事件和高性能运行时。Yio 通过稳定语义签名将两者连接：设计期仍是 AI 熟悉的 HTML，运行时则投影为 `Button`、`Slider`、`ListView` 等强类型对象。

这一设计避免了传统 DOM 式弱类型调用，也避免了引擎 UI 常见的全局句柄和字符串查找。CSS 可以改变布局与视觉，但不会改变对象身份，既方便 AI 推理，也方便大型游戏项目长期维护。

## 4 Rust 跨引擎核心与增量自绘管线

Yio 将布局、文本、动画、滚动、输入语义和渲染意图集中在 Rust 核心中，通过稳定 C ABI 接入引擎。公共 API 不依赖 Unity 类型，引擎后端不重复解析 HTML/CSS 或计算布局。

在性能上，项目采用持久布局树、文本测量缓存、增量渲染构建、帧数据列级增量、虚拟列表和图集页逐出等机制。它证明了面向 AI 的文本 DSL 与游戏运行时性能并不冲突，可以同时获得可生成性、确定性和运行效率。

## 5 AI 能力被产品化而非停留在开发过程

Yio 将 AI 操作说明、围栏参考、API 配方和安装流程作为产品的一部分随工具分发。CLI 的 stdout 可输出单一 JSON 文档，stderr 承载进度，退出码区分内容错误与工具错误；列表命令控制输出粒度，避免无意义地消耗模型上下文。

这些设计直接面向 AI Agent 的工作方式，使框架具备被不同模型、不同 IDE 和不同团队复用的基础，而不是只能依赖项目作者本人操作。

# 四、价值贡献

## 1 对目标问题的解决程度

Yio 已经打通 AI 参与游戏 UI 开发所需的关键链路：AI 可以读取标准文本源码，依据明确围栏生成或修改页面，通过自动检查修正错误，在浏览器中快速预览，打包为游戏资源，并在 Unity 中通过类型化 API运行和交互。

项目同时处理了“能写”“能看”“能验证”“能运行”“能维护”五个层面的问题。与只生成图片或网页 Demo 的方案相比，Yio 的产出是可进入版本库、可测试、可构建、可被业务代码操作的工程资产。

## 2 对研发效率和协作方式的价值

对程序员而言，Yio 减少了重复搭建界面层级、手工配置组件和跨场景维护 Prefab 的成本；标准文本便于批量修改、代码审查和自动化测试。对策划、设计和技术美术而言，浏览器预览降低了查看效果的门槛。对 AI 而言，统一语言、明确错误和可执行验证显著减少了反复猜测。

更重要的是，它改变了协作接口：团队不再要求 AI 学会操作每一种引擎编辑器，而是让 AI 围绕稳定的文本协议和命令行工具工作。引擎升级或后端变化时，设计源文件和大部分业务逻辑仍可保持稳定。

## 3 对产品质量的价值

围栏机制把大量问题从运行时提前到打包期，降低“预览正常、真机异常”或“不支持属性被静默忽略”的风险。类型化 API 和明确生命周期减少错误调用。差分测试、性能基准、ABI 检查和 CI 门禁让核心算法的演进有可重复证据。

在复杂场景中，增量布局和增量渲染构建已经取得明确性能收益，虚拟列表、字体图集、遮罩、滚动和资源逐出等能力也面向实际游戏 UI 负载设计。这使项目不只是 AI 概念展示，而具备继续向生产级框架演进的基础。

## 4 推广潜力

Yio 的方法具有较强的横向推广价值。

首先，它适用于需要大量界面内容、频繁迭代和多角色协作的游戏项目，如 RPG、模拟经营、卡牌、工具型应用和编辑器扩展。其次，Rust 核心与引擎后端分离，未来可扩展到 Godot 等引擎，降低多端或多引擎项目重复实现 UI 系统的成本。再次，标准 HTML/CSS 和 MIT 开源许可降低了学习与采用门槛，也便于高校、独立开发者和中小团队进行二次开发。

更广义地看，Yio 验证了一条可复用路径：当一个专业软件领域的私有表达不利于 AI 理解时，可以选择 AI 已具备强先验的标准语言，再用领域围栏、类型化运行时和自动验证把通用模型能力转化为可靠生产力。这一思路不仅适用于游戏 UI，也可迁移到可视化编辑、工业配置、交互原型和跨端内容生产等领域。

## 5 后续规划

项目下一阶段将继续完善 Unity 生产化体验，补充公开在线演示与完整视频，扩大真实项目试用和用户反馈；同时继续推进引擎无关 C# 层与第二引擎后端验证，检验“同一份 UI 源码跨引擎一致运行”的核心价值。随着真实用户增加，项目将进一步补充界面制作耗时、缺陷率、迭代轮次和跨端复用比例等量化指标。

# 申报页面推荐摘要

Yio 是一套为 AI 协作开发重新设计的跨引擎游戏 UI 框架。它使用标准 HTML/CSS 子集作为设计语言，让 AI 能直接阅读、生成和修改界面；通过围栏验证拒绝无法兑现的语法，将不确定的模型输出转化为可检查的工程输入；再由 Rust 核心完成布局、文本、动画、滚动、事件和自绘渲染，并通过类型化 C# API 接入 Unity。项目已经形成 AI 初始化、源码编写、浏览器预览、自动检查、资源打包和 Unity 运行的完整闭环，提供 CLI、桌面 GUI、Unity UPM 包、22 个展示页面及多层自动化测试。在约 2,400 节点场景中，增量布局相较全量重建取得约 9.5 倍提升。Yio 希望解决的不是“让 AI 画一张 UI 图”，而是让 AI 产出可验证、可运行、可维护并可跨引擎复用的游戏 UI 工程资产。
